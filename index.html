// about

I'm a second-year at NIT Kurukshetra, technically studying AI & ML, though most of what actually stuck came from watching distributed systems fall over and figuring out why. I like the kind of bug that only shows up under load, at scale, or on the fortieth test case, the kind that makes you actually understand what you built.

A few habits repeat across almost everything I've shipped: validate before you touch the network, write down every failure mode instead of hoping it won't happen, and if you inherit someone else's system, audit it before you trust it. One of the projects below is a port of an existing distributed search engine; I wrote my own production readiness report against it, then fixed most of what it flagged. That instinct mostly comes from competitive programming, where a judge rejects a wrong answer with zero sympathy and no partial credit.

1,300-plus problems in, Specialist on Codeforces, Guardian on LeetCode, still capable of losing to a segment tree on a bad day. I also help run competitive programming workshops for Open Code Developers at NIT KKR, mostly because explaining an algorithm out loud is the fastest way to discover I didn't fully understand it.

FEATUREDMAY-JUN 2026

SynapseAI

Seven AI agents that write, run, and grade their own machine learning code, so a full benchmarking pass takes minutes instead of days.

  • A Supervisor agent routes execution across six specialists (EDA, Preparation, Feature Engineering, Model, Critic, Report), all reading and writing one shared Blackboard state instead of talking to each other directly.
  • Every agent generates real Python with a local LLM (Ollama, Qwen3:8B) and runs it inside a sandbox that AST-validates the code, whitelists imports, blocks dangerous calls, and enforces a timeout before anything executes.
  • The Critic agent checks the leaderboard for overfitting and underfitting and can send the pipeline back for another training pass instead of accepting the top score blindly.
  • Auto-benchmarks 9 model families end to end, from Logistic Regression to CatBoost, and ships the winner as a serialized model plus a written report.

FEATUREDJAN-MAR 2026

Landslide Risk Mapping

163 million pixels of Himachal Pradesh elevation data, turned into a landslide risk model, then stress-tested across 10 algorithms to find out which one actually generalizes.

  • Built the full geospatial pipeline: DEM terrain features, OpenStreetMap infrastructure distances via STRtree indexing, satellite NDVI, and NASA POWER rainfall batched into under 100 API calls instead of thousands.
  • Reformulated 4 risk classes into 3, which improved every single model tested, not just the best one, by removing overlap between the two hardest categories to tell apart.
  • Evaluated 10 models across three paradigms (Bagging, Boosting, Deep Learning) on both label schemes: 19 experiments, one shared results ledger.
  • With no raw satellite imagery available, reconstructed real 16x16x12 spatial patches from point data alone to train a CNN, verified pixel exact against the tabular features at each patch's center.

02 Systems
MAR-MAY 2026

Distributed Search Engine

Ported an existing master, backup, and replica search engine from Python 2 to 3, audited it against production standards, then fixed most of what the audit found.

  • The design (popularity-triggered replicas, a standby master, two-phase-commit metadata sync) is adapted from an existing open-source project. My work was the port, the audit, and the hardening.
  • The Python 2 to 3 port surfaced bugs that only showed up at runtime, not at parse time, from Python 3's stricter iteration and I/O rules.
  • Wrote my own production readiness report against the freshly ported code, then fixed most of it: pooled MongoDB connections instead of one per query, LRU-bounded popularity counters instead of unbounded dicts, explicit timeouts on every RPC, graceful shutdown on SIGTERM.
  • What's still open is documented, not hidden: no transport security yet, and the two-phase commit has no rollback path exercised.

JUN-DEC 2025

Flyh, Flight Booking

An airline booking backend split into 4 microservices that won't double sell a seat when two people click buy at the same time.

  • Flight, Booking, Notification, and an API Gateway service, each independently deployable, talking over REST and one RabbitMQ queue.
  • Database transactions and row-level locking through Sequelize handle the real concurrency problem: two users booking the same seat at once.
  • Booking confirmations go out asynchronously over RabbitMQ so a slow email provider never blocks a booking response.
  • The gateway handles JWT auth, role-based authorization, and rate limiting in one place instead of in every service.

03 Also shipped
MLOps

Batch Pipeline

A small pipeline that turns OHLCV data into a trading signal, built to never fail silently.

  • Every failure mode gets its own path: missing config fields, bad YAML, a missing column, a window bigger than the dataset. Each one writes a structured error and exits non-zero instead of crashing.
  • Deterministic by construction. Same data and config means the same signal_rate every run.
  • One Docker build bundles the data and config, so it runs standalone with no flags or mounts.

Web tool

Page Pulse

Paste a URL, get its vitals: status, response time, title, missing alt text, word count.

  • Parsing is a pure function with no idea fetch, timeouts, or HTTP status codes exist, which is what makes the tests plain assertions instead of mocked network calls.
  • Five typed error codes instead of one generic failure, so the caller knows exactly what went wrong.
  • A target page that itself 404s is still a successful audit. Only Page Pulse's own failure to complete one counts as an error.

Futures Trading Bot

A CLI that places market, limit, and stop-market orders on Binance Futures, signing every request by hand.

  • Talks to the REST API directly with HMAC-SHA256 signing and no python-binance dependency, so the signing and error handling stay fully visible in the code.
  • Input validation never touches the network. A bad symbol or a non-positive quantity gets rejected before it can cost an API call.
  • Ships an offline dry-run mode that stubs the HTTP layer but runs the real client code end to end.
