// 01

Why sign a request at all

An exchange needs to know a request genuinely came from you and wasn't altered in transit, without you sending a password on every call. HMAC-SHA256 signing solves this: your request parameters get combined into a string, hashed together with a secret key only you and the exchange know, and that hash gets attached to the request. The exchange redoes the same hash on its end. If they match, the request is authentic.

The signature covers the exact request sent, so any tampering in transit breaks the hash and the exchange rejects it.

// 02

No wrapper library, on purpose

Using python-binance would have made signing someone else's problem. Talking to the REST API directly instead means the signing and error handling are fully visible in this codebase, not hidden inside a dependency, which matters both for understanding what's actually happening and for debugging when a request gets rejected.

// 03

Validate before you spend an API call

Exchanges rate-limit, and sending a malformed request just to discover it's malformed wastes a call you might not get back for a while. Every input, symbol, quantity, order type, gets validated locally first. A bad symbol or a non-positive quantity is rejected before it ever reaches the network.

// 04

Testing without touching real money

The offline dry-run mode stubs only the HTTP layer. Everything else, the real client, the real order-building and validation code, runs exactly as it would live. That means the whole pipeline is verifiable end to end without needing live API credentials or risking funds, even on testnet.
