The topology: master, backup, crawler, replica

Four node roles, each with one job. The Master holds the authoritative index and coordinates everything. A Backup stands by, ready to take over if the master goes down. A Crawler feeds new documents in, worth being upfront about: here it's a synthetic data generator rather than a live web crawler, which was a deliberate scope decision, not a hidden gap. Replicas serve read queries and get provisioned dynamically based on how popular a query pattern is.

The design itself, this topology, the popularity-triggered replication, the standby master, is adapted from an existing open-source project. What follows is the part that was actually built here: the port, the audit, and the hardening.

Crawler feeds the Master, which stays synced with a standby Backup and serves reads out to dynamically provisioned Replicas.

// 02

What breaks when you move from Python 2 to 3

Porting isn't just syntax. Several behaviors changed in ways that only surface at runtime, not when the code is parsed or imported. Dictionary methods like .items() started returning views instead of lists, which changes what happens if you mutate a dict while iterating over it. Integer division switched from floor division to true division by default. String and bytes handling got stricter about where the two can mix.

None of these show up as an import error. They show up as a wrong answer, sometimes only under a specific input, which is exactly the category of bug this port had to hunt down by hand.

// 03

Why two-phase commit

When the cluster's metadata needs to change in more than one place at once, say, registering a new replica, you can't just tell each node separately. If the process fails halfway through, some nodes have the update and some don't, and now the cluster disagrees with itself.

Two-phase commit avoids that by splitting the change into a prepare round ("can everyone do this?") before a commit round ("okay, everyone actually do it"). Nothing takes effect until every node has agreed it can, which makes the update all-or-nothing instead of partial.

// 04

What a production-readiness audit actually checks

After the port, the next step was writing a production-readiness report against the newly-ported code, then fixing most of what it flagged. Concretely, that meant: connections were being opened per query instead of pooled, now pooled. Popularity counters were a plain dictionary that grows forever, now bounded with an LRU cache. RPCs had no timeout, meaning one slow node could hang the whole system, now every RPC has an explicit one. And the process had no graceful shutdown, now it handles SIGTERM properly and finishes in-flight work first.

None of these are exotic. They're the unglamorous checklist that separates code that works on a laptop from code you'd trust on a server.

What is still open

Documented, not hidden: there is no transport security on the gRPC channels yet, and the two-phase commit's rollback path has not been exercised under real failure conditions. A production-readiness report is only useful if it is honest about what it did not fix yet.
